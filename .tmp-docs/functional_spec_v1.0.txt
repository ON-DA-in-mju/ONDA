1. 문서 개요
1.1 작성 목적
본 문서는 ON-DA 서비스의 화면, 기능, 데이터, 사용자 권한, 오류 처리 및 테스트 기준을 구체화하여 개발자·디자이너·기획자 간 구현 기준을 통일하기 위한 기능 명세서이다. 학생용 앱, 기사님용 앱, 관리자 웹 및 서버에서 제공해야 하는 기능의 입력 조건, 처리 방식, 출력 결과와 예외 상황을 정의하며, 설계·개발·테스트 과정에서 공통 기준으로 활용하는 것을 목적으로 한다.
1.2 기준 원칙
• 학생용 앱, 기사님용 앱, 관리자 웹 및 서버가 하나의 운행 데이터를 기준으로 동작하도록 한다.
• 기사님이 운행 시작 버튼을 누른 시점부터 위치정보 전송을 시작하고, 운행 종료 이후에는 위치 수집을 중단한다.
• GPS 좌표, 예상 도착시간 및 정류장 통과 여부는 정확도가 충분하지 않은 경우 확정 정보처럼 표시하지 않는다.
• 공식 시간표·운행 상태·공지는 학생 제보와 화면 및 데이터 구조에서 명확히 구분한다.
• 기사님의 운전 중 조작을 최소화하며, 운행 중단 요청과 같은 추가 입력은 안전한 장소에 정차한 뒤 수행하도록 안내한다.
• 사용자 역할과 소속 기관에 따라 조회·등록·수정·삭제 권한과 데이터 접근 범위를 제한한다
•오류나 네트워크 장애가 발생한 경우 오래된 데이터를 실시간 정보처럼 갱신하지 않고, 마지막 정상 수신 시각과 오류 상태를 표시한다.
•경진대회에서 구현할 필수 시제품 기능과 실제 학교 도입 이후의 확장 기능을 구분하여 관리한다.
•기능 구현과 테스트는 본 명세서에 정의된 입력 조건, 처리 방식, 예외 처리 및 인수 기준을 따른다.

4. 공통 UI·UX 규칙
구분
규칙
정보 신뢰도
GPS 기반 정보에는 마지막 수신 시각과 연결 상태를 함께 표시한다. 오래된 위치는 실시간처럼 이동시키지 않는다.
상태색상
정상/운행 중, 대기, 주의/지연, 오류/중단은 색상뿐 아니라 텍스트와 아이콘을 함께 사용한다.
공식·비공식구분
공식 공지는 “공식” 배지, 학생 제보는 “학생 제보” 배지와 안내 문구를 표시한다.
날짜·시간
날짜와 시간은 YYYY.MM.DD HH:mm 형식을 사용한다. 위치정보와 같이 최신성이 중요한 정보는 3분 전과 같은 상대시간을 우선 표시하며, 상세 화면이나 선택 시 정확한 수신 시각을 함께 제공한다..
빈 화면
데이터 없음과 오류를 구분하여 안내하고, 다음 행동 버튼을 제공한다.
로딩
3초 이상 소요 가능 작업은 스켈레톤 또는 진행 상태를 표시한다.
접근성
버튼 최소 터치 영역 44×44px, 텍스트 대비 확보, 상태를 색상만으로 구분하지 않는다.
확인절차
삭제·운행 종료·강제 종료·긴급 공지 발송은 확인 창을 제공한다.

10.2 좌표 검증 및 필터링
• 위도·경도 범위를 벗어난 값은 폐기한다.
• 이전 좌표 대비 비현실적인 속도로 이동한 값은 이상 좌표로 분류한다.
• 정확도 값이 기준보다 나쁜 좌표는 지도 표시보다 상태 판단에서 낮은 가중치로 사용한다.
• 동일 sequence 또는 동일 시각 데이터는 중복 저장하지 않는다.
• 오래된 recorded_at 데이터는 실시간 배포하지 않고 지연 수신 기록으로만 저장한다.

10.4 현재 구간 및 통과 추정
서버는 단일 GPS 좌표가 아니라 최근 연속 좌표, 정류장 반경 진입·이탈, 이동 방향, 노선 순서를 함께 사용한다. 확실하지 않은 경우 “정류장 통과”가 아니라 “정류장 통과 추정” 또는 “위치 확인 중”을 제공한다.
10.5 예상도착시간
구분
처리
기본 계산
현재 위치와 다음 정류장 거리, 최근 이동속도, 노선 순서를 이용한다.
표시
“약 4분 후”처럼예상값임을 명시한다.
숨김조건
최근 위치 없음, GPS 정확도 불량, 네트워크 단절, 비정상 이동, 정차 장기화
우선정보
정확한 도착 시각보다 현재 구간·이동 방향·운행 여부를 우선 제공한다.
향후확장
누적 운행 데이터와 시간대별 교통 패턴을 반영할 수 있다.

12.1 주요 제약조건
• 하나의 trip에는 동일 차량이 중복 배정될 수 없다.
• 동일 기사 또는 차량의 시간이 겹치는 배정은 차단한다.
• 운행이 시작된 뒤 route_id, scheduled_start 등 핵심 필드 변경은 제한한다.
• 학생 제보는 만료 시각을 필수로 두며, 일반 화면에는 작성자 개인정보를 노출하지 않는다.
• 위치 기록은 보관 정책에 따라 삭제 또는 집계 데이터로 변환한다.

14. 상태 전이 및 업무 흐름
14.1 정상 운행 흐름
1. 관리자가 운행 일정과 차량·기사를 등록한다.
2. 서버가 배정 정보를 기사님용 앱에 전달한다.
3. 기사님이 운행 전 자동 점검을 완료한다.
4. 기사님이 운행 시작을 누르면 상태가 RUNNING으로 변경되고 위치 전송이 시작된다.
5. 서버가 좌표를 검증하고 학생·관리자에게 현재 구간과 상태를 배포한다.
6. 기사님이 운행 종료를 누르면 위치 전송이 중단되고 COMPLETED로 전환된다.
14.2 배정 변경 흐름
1. 관리자가 운행 상세에서 차량·기사·시간을 변경한다.
2. 서버가 중복·시간 충돌·운행 상태를 검증한다.
3. 변경 버전을 증가시키고 감사 로그를 저장한다.
4. 기존 기사에게 취소 또는 변경 알림, 신규 기사에게 새 배정 알림을 전송한다.
5. 기사 앱은 최신 버전의 배정만 표시하고 미확인 변경 배지를 노출한다.
14.3 운행 중단 흐름
1. 기사님이 안전한 장소에 정차한 뒤 중단 요청을 제출한다.
2. 상태가 STOP_REQUESTED로 변경되고 관리자에게 긴급 알림이 전달된다.
3. 관리자가 사유와 영향을 확인해 승인 또는 반려한다.
4. 승인 시 SUSPENDED로 변경하고 학생 화면 및 공식 공지에 반영한다.
5. 필요 시 대체 차량을 배정하고 기존·신규 기사에게 알림을 전송한다.

18.1 시제품 완료 기준
• 학생용 앱, 기사님용 앱, 관리자 웹이 하나의 운행 데이터를 공유한다.
• 실제 또는 모의 GPS가 이동하고 같은 노선의 여러 차량이 구분된다.
• 위치정보가 끊기면 마지막 수신 시각과 오류 상태가 정확히 표시된다.
• 운행 배정 변경 시 기사님에게 알림이 전달되고 앱 정보가 갱신된다.
• 공식 공지와 학생 제보가 명확히 구분된다.
• 핵심 데모 시나리오가 재현 가능하고 중대한 오류 없이 완료된다.
